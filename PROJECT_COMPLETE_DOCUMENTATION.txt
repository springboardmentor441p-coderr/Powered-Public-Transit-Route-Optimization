======================================================================
1. PROJECT OVERVIEW
======================================================================

Title
RouteRanker - AI-Powered Public Transport Route Analysis and Optimization

Problem statement and solution
GTFS feeds contain linked route, trip, stop and timetable tables. Inspecting a
large feed manually makes it hard to compare scheduled service, stop coverage
and route overlap. RouteRanker validates the supplied Chennai Metropolitan
Transport Corporation (MTC) feed, generates descriptive analyses and
route/stop features, groups routes using unsupervised models, and presents the
processed results in a web application.

Implemented objectives
- Read and validate the actual GTFS ZIP and produce typed Parquet tables.
- Analyze routes, stops, scheduled trips, service times, headways, route-stop
  coverage and shared-stop Jaccard similarity.
- Build documented raw and normalized route, stop and route-pair features.
- Fit K-Means and DBSCAN on supported schedule and stop-network features.
- Expose generated summaries and saved results through a read-only API.
- Display API results in a responsive React and TypeScript application.

Scope and potential users
Potential users include students, mentors, analysts and transit planners who
need to examine this feed. Current use cases are route/stop search, scheduled
feature comparison, headway/hour inspection, stop membership exploration and
cluster profile review. There is no login system or external deployment.
Despite the project title, there is no schedule optimization solver or
explainable schedule what-if module in the current source. Models do not
recommend adopted service changes. There is no passenger demand, occupancy,
congestion, actual travel-time or real-time vehicle prediction.

======================================================================
2. PROJECT ARCHITECTURE
======================================================================

Architecture and data flow
1. data/raw/mtc-gtfs.zip is the preserved source.
2. backend/src/routeranker/ingestion reads GTFS text members, validates them,
   and writes Parquet and quality reports to data/processed/gtfs/.
3. The analysis module reads GTFS Parquet and writes EDA outputs to
   data/processed/eda/.
4. Feature engineering checks source/EDA values and writes route, stop and
   pair features to data/processed/features/.
5. Clustering fits/evaluates models and writes predictions, profiles and
   models to data/processed/clustering/.
6. FastAPI reads and caches these local files and returns typed JSON. API
   requests do not ingest or retrain models.
7. React pages call the API with Axios and render tables, Recharts charts and
   Leaflet stop markers.

Storage and database status
Persistence is local files: Parquet, CSV, JSON, Markdown, PNG and joblib.
There is no active SQL database or database server. DuckDB is declared only as
an optional analytics dependency and is not imported by the current code.
Pandas is not imported. Polars is the dataframe engine used by preprocessing
and API reads.

The default browser API base is http://127.0.0.1:8000/api/v1. CORS is
restricted to configured origins. The map uses actual GTFS stop coordinates
and does not connect markers into invented route geometry.

4. DATASET AND DATA PREPROCESSING
======================================================================

Source and files
The community source is https://github.com/ungalsoththu/ChennaiGTFS. The local
input data/raw/mtc-gtfs.zip contains these available files and Phase 1 row
counts, excluding headers:
agency.txt 1; calendar.txt 6; feed_info.txt 1; routes.txt 4,611;
stop_times.txt 1,360,443; stops.txt 5,580; trips.txt 47,047.

GTFS table purpose
- agency.txt: operator name, ID, URL and timezone.
- routes.txt: route_id, route labels, route_type and agency association.
- trips.txt: trip_id linked to route_id, service_id and direction_id.
- stops.txt: stop_id, stop_name and stop_lat/stop_lon.
- stop_times.txt: trip/stop links, stop_sequence and scheduled arrival/
  departure time.
- calendar.txt: weekday service flags and date interval.
- calendar_dates.txt (absent): date-specific service additions/removals.
- frequencies.txt (absent): headway-based service patterns.
- shapes.txt (absent): route geometry points.
- feed_info.txt: publisher/feed information.

Validation and outputs
Ingestion reads text values as strings first. It checks required files and
columns, key duplicates, blank values, numeric conversions, coordinate bounds,
GTFS time syntax, stop sequence and within-trip time regressions, and agency/
route/trip/service/stop relationships. It preserves raw columns and adds
numeric/time convenience fields such as stop_lat_value, route_type_value and
arrival_time_seconds. Issues are reported; data is not silently discarded.
Critical errors produce failed status while warnings remain visible. If
calendar_dates.txt is absent, an empty typed calendar_dates.parquet is written
and the report records its absence.

The report records 4,611 routes, 3,934 routes referenced by trips (677 unused),
5,580 stops, 5,477 stops referenced in stop_times, 47,047 trips and 1,360,443
stop_time rows. Four calendar service rows are not used by trips. EDA records
96,013 route-stop pairs. It reports no full-row duplicates, no duplicate
primary keys and no unresolved unique references, plus two Phase 1 blank-value
warnings. These are facts about this archive snapshot, not current live
operations.

Time parsing
GTFS allows hours above 24 for after-midnight schedules. parse_gtfs_time
converts HH:MM:SS to seconds since service-day start and preserves the original
text. For example 25:10:00 is 90,600 seconds. The source report found a maximum
hour of 25 and 1,904 stop-time rows after 24:00; tests cover this behavior.

Missing files and data limits
calendar_dates.txt, frequencies.txt and shapes.txt are unavailable. The
analysis has no date-specific exceptions, frequency-based service, supplied
route geometry, route length or geographic route area. Stop markers do not
represent bus paths. No real-time, fare, passenger, occupancy or traffic data
is present. The community feed is a snapshot, not a guarantee of current
official operations.

6. FEATURE ENGINEERING
======================================================================

backend/src/routeranker/features/engineering.py generates raw and normalized
route, stop and route-pair data. source_validation.py independently checks
source-derived route metrics. The report records 42 validation checks passed,
39 dictionary definitions, 4,611 route rows, 5,580 stop rows and 923,449
route-pair rows.

Route features include scheduled trip record count, unique stops, average
scheduled first-stop headway, headway interval count, template-week peak and
off-peak departures, first/last departure time, service span, shared-stop
count/ratio, source labels and missingness indicators. Peak windows are
07:00-10:00 and 16:00-19:00 by project definition, not official MTC labels.

Stop features include routes serving each stop and scheduled trip/stop-time
references. These references are not boardings. Pair features include shared
stop count, unique-stop counts for each route and Jaccard similarity
(intersection divided by union of stop sets). Jaccard is network overlap, not
congestion or passenger substitution.

Numeric normalization is median imputation followed by StandardScaler
z-scores. Identifiers are not scaled. Missing raw values and indicators are
retained; normalization parameters are output. Generated files include route,
stop and pair features in CSV/Parquet, normalized counterparts,
feature_dictionary.csv/.md, normalization_parameters.json,
feature_engineering_report.json/.md and feature_validation_report.json/.md.

======================================================================
7. MACHINE LEARNING
======================================================================

Purpose and models
This is unsupervised grouping, not prediction of a labeled target. The feed
has no passenger-demand or occupancy labels.

K-Means partitions feature vectors around centroids. The pipeline evaluates
k=2 through 10 and saves k=6, n_init=20, seed=42.
DBSCAN identifies dense groups and labels sparse routes as noise. The saved
configuration uses eps=1.1435182896, min_samples=8, Euclidean distance; eps
candidates use nearest-neighbor distance quantiles. DBSCAN cannot predict for
unseen routes without refitting.

The algorithms are complementary: K-Means provides a fixed partition that is
easy to profile, while DBSCAN can represent dense groups and mark sparse
routes as noise without requiring a preset cluster count. They were selected
for these unsupervised grouping behaviors, not because either is proven
superior on a labelled outcome. Evaluation uses internal metrics and profiles.

The seven selected features are total_scheduled_trip_records,
unique_stop_count, average_first_stop_headway_seconds, peak_departure_share,
scheduled_service_span_seconds, shared_stop_ratio and headway_missing.
Selected positive magnitude/time fields receive log1p; preprocessing applies
median imputation and StandardScaler fitted on active routes. A missingness
indicator retains the fact of headway imputation. 677 routes with no trip
records are excluded from fit but retained with an exclusion status. IDs and
names are not model inputs; redundant or constant columns are documented in
feature_selection.json.

Each saved joblib dictionary contains a fitted preprocessing/model pipeline
and feature-schema/fit metadata. Its preprocessing applies selected log1p
transforms, median imputation and scaling before K-Means prediction or DBSCAN
fit-label inspection. Phase 4 creates these artifacts; the API reads them
only for saved metadata and does not refit on requests.

Profiles compare original-scale features. Noise is only a feature-space
density label. Silhouette and Davies-Bouldin are internal diagnostics without
ground-truth labels; silhouette is computed on a 2,000-route sample here.

Actual saved/reproduced metrics:
- K-Means: 6 clusters, 3,934 inliers, zero noise; silhouette 0.3854219,
  Davies-Bouldin 0.939803. Cluster sizes for IDs 0-5 are 722, 793, 1,451,
  668, 63 and 237.
- DBSCAN: 4 non-noise clusters, 3,898 inliers and 36 noise routes; silhouette
  0.3891479, Davies-Bouldin 0.670619. Cluster sizes 0-3 are 3,024, 198, 667
  and 9; noise label -1 has 36 routes.

Generated artifacts include kmeans_model.joblib, dbscan_model.joblib,
cluster_predictions.csv/.parquet, cluster_sizes.csv,
cluster_profiles.csv/.parquet, model_comparison.csv, candidate metric CSVs,
feature_selection.json, feature_quality_profile.csv,
feature_quality_report.json, standardized model matrices,
model_parameters.json, selected_feature_correlations.csv, PCA coordinate/
variance tables and chart, and machine_learning_report.json/.md. The API does
not expose PCA coordinates, so the frontend does not draw PCA.

Compatibility issue
The saved joblib pipelines were serialized with scikit-learn 1.5.0.
backend/pyproject.toml pins scikit-learn==1.5.0 and numpy<2.0. The active
project .venv has scikit-learn 1.9.1 and NumPy 2.5.4. It emits
InconsistentVersionWarning and a real K-Means prediction fails with
AttributeError because SimpleImputer lacks _fill_dtype. With a separate
Python 3.12 installation using scikit-learn 1.5.0 and NumPy 1.26.4, model
loading worked and K-Means predictions/DBSCAN saved labels matched all 3,934
active routes. A seed-42 actual-feature workflow run also succeeded in
temporary output without replacing the saved Phase 4 models. The active .venv
still needs alignment. API assignments come from saved tables; no per-request
retraining or new-route prediction endpoint exists. Load only trusted joblib
files.

======================================================================
14. LIMITATIONS AND FUTURE ENHANCEMENTS
======================================================================

calendar_dates.txt absence means date exceptions are unavailable.
frequencies.txt absence means frequency-based service is not represented.
shapes.txt absence means route geometry and lengths are unavailable.
There is no real-time tracking, passenger-demand prediction, congestion
prediction, occupancy classification or actual travel-time measurement.
Headways and counts are schedule-derived, not delivered service observations.
The community dataset is a snapshot and has no labelled ground truth for
cluster evaluation. OpenStreetMap tile availability depends on network access.

Possible future work, not implemented: use authorized updated GTFS feeds;
incorporate exceptions/frequencies/shapes when provided; add clearly
hypothetical schedule scenarios; expose PCA coordinates if wanted; add
reproducible dependency locks, accessibility/browser testing, monitoring,
security review and deployment automation. Never fill unsupported passenger
or route-geometry values with fabricated data.

16. PROJECT SUMMARY
======================================================================

RouteRanker implements a local GTFS-to-dashboard path: validation, descriptive
schedule analytics, engineered route/stop/pair features, unsupervised route
clusters, a typed API and a React frontend. It demonstrates Python data
processing, feature engineering, clustering and evaluation, API design,
TypeScript integration and automated testing.

Phases 1-6 are implemented. Phase 7 local integration and build checks pass,
but release readiness is partial: HTTPX-dependent tests are skipped and the
active environment cannot safely predict with the saved models until its
versions are aligned. A connected dependency audit and deployment
infrastructure checks remain. The project has not been publicly deployed and
does not make passenger-demand, congestion, occupancy or real-time
predictions.
